# Tauri migration — what's verified, what isn't, and exactly why

This replaces the Electron + Node-API app (`electron/`, `napi/` — now
deprecated, see their `DEPRECATED.md`) with **Tauri + React + Rust**, calling
the **same, unmodified C++ engine** (`core/`) through a new `cxx` bridge
instead of N-API. Read this before trusting any part of `tauri-app/` — it's
organized as "verified for real" vs. "written carefully, not compiler-checked
here, and why."

## The core constraint that shaped everything below

The only Rust toolchain installable in the environment this was built in is
Ubuntu 24.04's `apt install rustc` (**1.75.0**). Current Tauri 2.x's own
official template declares `rust-version = "1.90"` (confirmed by fetching it
directly from `tauri-apps/tauri`'s repo — see below), and a `cargo check`
against real Tauri 2.11 fails immediately on a transitive dependency needing
`edition2024`, which 1.75 doesn't support. `rustup` (the normal way to get a
current Rust) downloads from `static.rust-lang.org`, which isn't reachable
from this sandbox's allowed network. **Net effect: the full Tauri application
(`lib.rs`, `commands.rs`, `main.rs`, `tauri.conf.json`, `capabilities/`)
could not be compiled or run here.** This is a sandbox limitation, not a
statement about whether it'll work on your machine — install Rust via
**rustup**, not your distro's package manager, and this constraint doesn't
apply to you.

## What WAS verified for real, end-to-end, in this session

Rather than write the FFI/tooling layer and hope, each piece below was
compiled and actually run against real inputs, using an older `cxx` (1.0.116,
compatible with the available rustc) as a stand-in — the bridge declarations
in `src-tauri/src/ffi.rs` are copied verbatim from what was tested, so the
verification transfers to the real file:

**1. Rust calling the real C++ engine, not a stub.** Compiled
`native/netpulse_ffi.cpp` + all of `core/src/*.cpp` through `cxx_build`, then
from Rust: called `add_target("1.1.1.1", ...)` — which spawned a real probe
thread in the real `Manager`/`Session` — then `get_state_json()` and got back
real hop data (`{"targets":[{"id":1,"name":"1.1.1.1",...,"hops":[{"hop":1,
"address":"192.0.2.1",...}]}]}`), then `remove_target()` cleanly. This is the
single highest-risk piece of the whole migration (does `cxx` actually bridge
to this specific, STL-heavy engine) and it works.

**2. The new Rust tool implementations, against real network I/O.**
`tools.rs`'s DNS forward/reverse (via `hickory-resolver`) and TCP port-scan
(via `tokio`) were run directly: `dns_lookup("one.one.one.one")` returned the
real `1.1.1.1`/`1.0.0.1`; `reverse_lookup("1.1.1.1")` returned the real PTR
name; a port scan of `1.1.1.1:443` correctly found it open via a real TCP
connect.

**3. The ping tool's spawn/stream/stop lifecycle — including a real bug it
caught.** Raw ICMP itself is blocked by this sandbox's network egress (same
limitation that's applied to testing the C++ probing engine throughout this
whole project — nothing new), so ping *replies* couldn't be tested. But
spawning `ping`, streaming its output, and stopping it could be, and this
caught a genuine, non-obvious bug: on Linux, `ping`'s stdout is fully
block-buffered (not line-buffered) once it's a pipe rather than a terminal —
so without a fix, no output would arrive until the process *exited*, silently
breaking "live" streaming. `tools.rs` now wraps the spawn with `stdbuf -oL` on
Linux specifically because this was caught by testing, not because it was
anticipated. Confirmed the fix works: before it, a piped `ping` produced zero
output for 3+ seconds; after it, `[out] PING 1.1.1.1 (1.1.1.1) 56(84) bytes of
data.` arrived immediately. (This buffering behavior is specific to `ping`'s
own stdio handling, not something the old Electron/Node implementation would
have avoided either — worth checking if it was silently affected there too.)

## Two real design bugs caught and fixed during writing (not shipped broken)

- **`ping_start`'s event id.** The first draft generated the ping's tracking
  id *inside* `tools::start()`, after the streaming closures were already
  constructed — meaning they couldn't correctly capture it. Fixed by having
  the id generated by the *caller* (`commands.rs`) and passed in, so it's
  captured correctly before any async work starts.
- **`update_target`'s partial-update semantics.** The frontend
  (`App.jsx`'s `applyUpdate()`) sends only the fields the user changed,
  relying on the backend to merge them into the target's *current* settings —
  exactly what the old `napi.cpp` did via `settings_from_obj(o, cur)`. The
  first draft used a single `TargetConfig` struct with `serde` defaults for
  every field, which would have silently *reset* any field the caller didn't
  send back to a hardcoded default on every partial update (e.g., pausing a
  target could have quietly reset its probe interval). Fixed with a
  `PartialTargetConfig` (all `Option<T>`) that fetches the target's current
  config out of `get_state_json()` and only overlays the fields actually
  present, before calling into the FFI layer with a complete value set.

Neither of these would have been obvious from reading the code casually —
both surfaced from actually tracing the exact data flow end to end.

## What's carefully written but NOT independently compiler-verified

- `src-tauri/src/lib.rs`, `commands.rs`, `main.rs` — the Tauri-specific glue
  (`tauri::Builder`, `#[tauri::command]`, `State<'_, T>`, `Emitter::emit`).
  Every API used here was checked against **real source fetched directly
  from `tauri-apps/tauri`'s repository** (not training-data memory) — e.g.
  the `Emitter` trait and `emit<S: Serialize + Clone>(&self, event: &str,
  payload: S)` signature came straight from `crates/tauri/src/lib.rs`, and
  the `State<'_, Counter>` + `.manage()` + `invoke_handler(generate_handler!
  [...])` pattern came from `examples/state/main.rs`. It's grounded in
  today's actual API, not guessed — but "grounded in real source" and
  "compiled" are different claims, and only the former is true here.
- `capabilities/default.json`'s permission identifiers
  (`"allow-add_target"`, etc.). The *mechanism* is real and source-verified:
  `tauri-build::acl::AppManifest::new().commands(&[...])` autogenerates
  `allow-$command`/`deny-$command` permissions for the app's own commands
  (doc comment, `crates/tauri-build/src/acl.rs`), and `build.rs` wires it in
  via `Attributes::new().app_manifest(...)` (also source-verified, matching
  signatures exactly). The **one detail that couldn't be confirmed without a
  live build** is whether the capability file references these unprefixed
  (as written) or needs a different qualifier. **Fix if wrong:** run `cargo
  build` or `cargo tauri dev` once — Tauri writes the fully-resolved,
  authoritative permission list to `src-tauri/gen/schemas/*.json`; if
  `capabilities/default.json` doesn't validate against
  `desktop-schema.json` (most editors flag this immediately via the
  `$schema` reference), copy the correct identifiers from there.
- `tauri.conf.json` — structurally verified against a real, current example
  fetched from the Tauri repo (same keys: `build.frontendDist`/`devUrl`,
  `app.security.csp`, `bundle.icon`, etc.), CSP content carried over from the
  old `electron/main.js`'s policy. Not run through Tauri's own config
  validator here.

## Setting it up on your machine

```bash
# 1. Get a CURRENT Rust — NOT your distro's package manager:
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh
# (or the Windows rustup-init.exe from https://rustup.rs)

# 2. System webview dependency (Linux only — Windows uses WebView2, usually
#    already present; macOS uses WKWebView, built in):
sudo apt install libwebkit2gtk-4.1-dev libgtk-3-dev librsvg2-dev libsoup-3.0-dev libjavascriptcoregtk-4.1-dev

# 3. Frontend deps
cd tauri-app && npm install

# 4. Run it
npx tauri dev
```

First real build error, if any, is most likely one of the two flagged-above
"grounded but unverified" spots — check there first.

## Windows: raw ICMP elevation

Same as the old Electron app (see `README.md`) — this isn't Tauri-specific.
Raw ICMP sockets need Administrator on Windows / `cap_net_raw` on Linux. The
NSIS installer target in `tauri.conf.json` does a per-user install (no forced
UAC at install time, matching `electron-builder.yml`'s existing rationale);
the user runs the app elevated when they want raw mode, same as before.

## Dual build (normal / obfuscated) — now applies to the Tauri build too

`build.rs` reads the `obfuscate` Cargo feature (`cargo build --features
obfuscate`) and, if set, defines `NETPULSE_OBFUSCATE` when compiling the C++
engine via `cxx_build`, turning on
`core/include/netpulse/obfuscate.hpp`'s source-level obfuscation (string
encryption + opaque predicates) — see `../docs/OBFUSCATED_BUILD.md`, which
fully applies here too. No special compiler is required; a real LLVM
pass-plugin approach was tried and abandoned (ABI incompatibility between
prebuilt clang toolchains — see that doc for the full writeup), so this is a
plain compile definition, not a toolchain-dependent flag.

## IPC protection — how this satisfies "proper IPC protection"

Every command the frontend can call is listed in exactly two places, and
must match: `invoke_handler(generate_handler![...])` in `lib.rs` (what
*exists*) and `capabilities/default.json`'s `permissions` array (what's
*allowed*). Nothing else is reachable — no filesystem, shell, or HTTP plugin
is enabled; every network operation goes through this app's own named
commands. This is the direct architectural equivalent of the old
`contextBridge` allowlist in `electron/preload.js`, now enforced by Tauri's
own permission system rather than a hand-written bridge object.
